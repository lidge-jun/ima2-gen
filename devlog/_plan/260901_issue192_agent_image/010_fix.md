# wp2 — Fix

## 1. MODIFY `lib/agentImageVideoGen.ts` — forward the session image on the Responses branch

The defect: atlascloud/minimax/grok each call
`loadAgentCurrentImageReferences(ctx, sessionId, options.sourceImagePolicy ?? "none")`,
but the Responses branch passes a literal empty array.

The sixth positional argument to `generateViaResponses` changes from `[]` to
`await loadAgentCurrentImageReferences(ctx, sessionId, options.sourceImagePolicy ?? "none")`,
matching the atlascloud/minimax/grok branches exactly.

**Audit blocker 1 (amended).** The first draft planned a `{b64, mime}` adapter on the
theory that the Responses API wants a different shape. That was WRONG and actively
lossy: `ReferenceRef` (`lib/responsesImageAdapter.ts:163`) is
`string | { b64?, detectedMime?, declaredMime? }` — there is no `mime` field at all, so
the adapter's `mime` would have been dropped on the floor and `normalizeRef`'s
`declaredMime` fallback lane destroyed. `GrokReferenceImage`
(`lib/grokImageCore.ts:55-60`) is already structurally assignable to that arm, so the
correct fix is to pass the existing helper's result straight through. No bridge, less
code, both mime lanes preserved.

Constraint: this must NOT appear inside the `generateViaNai(...)` call slice —
`tests/nai-routing-contract.test.ts:84` fails if any nai slice contains a references key.

Activation scenario: repro C (session image + `sourceImagePolicy: "current"`) asserts
`input_image` appears in the outgoing Responses body. It fails before this change.

## 2. MODIFY `lib/agentQueueStore.ts` + `lib/agentQueueWorker.ts` — stop dropping the cause

`lib/agentQueueWorker.ts:182` already computes `rawCode`; `failAgentQueueItem` throws it
away because the signature and table have no column for it. The Agent composer reads
the QUEUE, so today the user only ever sees the generic wrapper.

Add a nullable `error_raw_code TEXT` via `addColumnIfMissing` (the exact pattern used
for `error_code` at `lib/db.ts:247`), then plumb it through. Storing it inside
`error_class` was rejected: that conflates two different meanings.

**Audit blocker 2 (amended) — every write path that CLEARS the error columns must also
clear the new one, or a stale rawCode leaks into a later success.** The four sites in
`lib/agentQueueStore.ts`: `claimNextAgentQueueItem` (:163),
`completeAgentQueueItem` (:178), `cancelAgentQueueItem` (:201), and
`retryAgentQueueItem` (:276). Plus `markRunningItemsFailed` (:218) sets its own code.
Read paths that must project the column: the three SELECT projections (:66-88, :93-119,
:135-152), the `AgentQueueRow` type (:15-32), `queueItemFromRow` (:287), and
`AgentQueueItem` in `lib/agentTypes.ts:58,70`.

Activation scenario: a queued turn whose upstream returns a failed image call must
surface `rawCode: IMAGE_TOOL_FAILED` from the QUEUE row, not just from `/turns`.

## 3. MODIFY `lib/agentImageVideoGen.ts` — reject an empty artifact

`agy` and `atlascloud` can resolve with an empty `b64` (0-byte artifact or 0-byte HTTP
200 body). `persistAgentImage` then writes a 0-byte file and registers it as a real
image. A silent empty artifact is worse than an error, so guard at the shared choke
point, before `persistAgentImage`:

```ts
if (!response.b64) {
  const err = new Error("Provider returned an empty image.") as Error & { code?: string; status?: number };
  err.code = "PROVIDER_EMPTY_IMAGE";
  err.status = 502;
  throw err;
}
```

**Audit blocker 7 (amended):** the Responses branch already self-guards at
`lib/responsesImageAdapter.ts:344`, so this guard's real coverage is
agy/atlascloud/minimax/nai/grok — "one guard covers every provider" was overstated. It
also cannot catch non-empty but corrupt base64; recorded as a known limit.

**Audit blocker 6 (amended) — retry decision, argued both ways.** The repo's own
precedent (`lib/agentRuntime.ts:365-372`) retries `IMAGE_TOOL_FAILED` because a
transient per-call failure often succeeds immediately after, and a 0-byte atlascloud CDN
download (`lib/atlasCloudImageAdapter.ts:177-183`) is exactly that kind of transient.
That argument won: `PROVIDER_EMPTY_IMAGE` IS added to `RETRYABLE_NO_IMAGE_CODES`. One
cheap automatic retry beats surfacing a hard failure for a hiccup, and if the second
attempt is also empty the user still gets the specific code. Verified separately that
the guard message does not contain `"No image data"`, so it cannot be swallowed by the
substring branch of `isTextOnlyResult`.

**Audit blocker 3 (amended) — the new code must be renderable.** `PROVIDER_EMPTY_IMAGE`
gets an entry in `ui/src/lib/errorCodes.ts` plus i18n keys in all four locales;
otherwise `resolveErrorSpec` degrades it to the generic UNKNOWN card, which is the same
class of defect as the queue rawCode drop being fixed above.

Activation scenario: a stubbed adapter resolving an empty `b64` must produce
`PROVIDER_EMPTY_IMAGE` and write NO file.

## Non-goals (recorded, deliberately not done)

- `STREAM_PARSE_FAILED` stays out of the retry set: a malformed stream is not obviously
  transient, and the UI already gives it a dedicated retry card.
- The `"No image data"` substring check in `isTextOnlyResult` stays. It is redundant for
  every classified code today, but it is a cheap net for an uncoded provider error.
- **The direct `POST /turns` route stays edit-incapable** (audit blocker 5):
  `lib/agentRuntime.ts:78` hardcodes `sourceImagePolicy: "none"`. The Agent composer
  uses the QUEUE (`ui/src/lib/agentApi.ts:100`), so real users are covered by this fix;
  changing the direct route's hardcoded policy is a separate API-contract decision and
  is NOT done here.
- Corrupt-but-non-empty base64 is not detected (audit blocker 7); only emptiness is.
